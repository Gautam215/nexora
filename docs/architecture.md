# Architecture Baseline

## Product Contract

The complete Nexora PRD is the source of truth. No project workflow uses mock data: account, organization, project, milestone, task, Kanban, task activity, comments, mentions, project activity, in-app notifications, private task files, permission-aware workspace Search, and the project analytics dashboard use PostgreSQL-backed APIs. Task files use PostgreSQL metadata/RLS and a server-only private filesystem store with short-lived signed access. Search uses the `0013` full-text-index migration; `0014` enables its rate-limit scope. `0017` enables task-file rate limiting, `0018` adjusts soft-delete visibility, `0019` raises the accepted quota ceiling, `0020` serializes milestone graph checks, `0021` saturates rate-limit counters and adds authorized per-project graph mutation locks, and `0022` locks authorized file downloads without broadening viewer table grants. Project analytics reuse existing tables and add no schema migration. The prior audit passed 82 tests against disposable PostgreSQL 16.12 with zero skips. This continuation adds comment-schema wiring and per-entity Search authorization cases; its database tests were skipped here because no test database is configured, so those additions still need PostgreSQL verification. Realtime and AI remain unavailable.

## Current Decisions

- **Web:** Next.js App Router, React, TypeScript, strict type checking.
- **Authoritative data:** PostgreSQL. Schema changes are immutable, numbered SQL migrations applied by a separate migration role.
- **Database access:** `pg` connection pool with bounded connection, statement, and query timeouts. All user and organization context is transaction-local so pooled connections cannot retain another request's context.
- **Tenant authorization:** `withOrganizationContext` verifies the authenticated user's active membership before it sets organization context or calls tenant-scoped business logic. RLS independently scopes identity, membership, invitation, audit, project, project-membership, milestone, task, task-comment, task-comment-mention, task-file, notification-preference, notification, workflow-status, dependency, and project-mutation-idempotency tables. Task files require project access to read and work permission to upload, replace, or soft-delete. Notifications force RLS; recipients can only read or update their own project-visible records.
- **Roles:** Organization roles are `owner`, `admin`, `member`, and `guest`. Project roles are `manager`, `member`, and `viewer`; project ownership is tracked separately. Organization managers retain project-management authority, while project roles never grant workspace-wide authority. Unknown roles fail closed.
- **Secrets and DB privileges:** `DATABASE_URL` is the restricted runtime role; `MIGRATOR_DATABASE_URL` is the schema owner/migration role. Neither value belongs in source control. The runtime role must not own tables or bypass RLS.
- **Private files:** `NEXORA_PRIVATE_FILE_DIR` points to a server-only directory outside `public/`; objects use opaque UUID names and restrictive directory/file permissions. `NEXORA_FILE_SIGNING_KEY` is a server-only 32-byte-or-longer secret. Signed links bind the user, tenant, task, file and file version for five minutes; access rechecks current membership and file state. Never log link query parameters or expose storage keys. The runtime role can soft-delete through scoped updates but cannot hard-delete file rows.
- **Security headers:** frame denial, MIME sniffing protection, `no-referrer`, and a restrictive permissions policy are enabled. `src/proxy.ts` generates a per-request nonce CSP for page responses; the request-time root layout lets Next.js apply the nonce to its generated scripts/styles. Dynamic progress bars use semantic `<progress>` elements rather than inline style attributes. Static assets and API routes are excluded from the proxy matcher and retain their own response-header paths. Unit tests cover policy construction; local HTTP smoke checks confirmed the CSP and nonces on rendered scripts for the home and login pages. Production browser/deployment verification remains. An unsafe inline-script policy is intentionally not used as a shortcut.
- **Authentication:** passwords use Node scrypt with random salts; opaque sessions and single-use verification/reset tokens are stored only as SHA-256 hashes. Sessions use host-only, `HttpOnly`, `SameSite=Strict` cookies and `Secure` in production. Login and recovery use bounded JSON, Zod validation, same-origin/Fetch Metadata checks, and fixed-window PostgreSQL rate limits with HMAC-derived subjects.
- **Invitations:** raw invitation tokens are emailed once and stored as hashes. Acceptance requires an active, email-verified account matching the invited address; the database function accepts a token once, records membership and audit data transactionally, and rejects replay. The browser removes the token from the address bar and holds it in tab-scoped session storage while the invitee signs in.
- **Email and rate-limit configuration:** outbound verification, reset, and invitation links use SMTP with TLS by default and the canonical `APP_ORIGIN`. Post-login return paths are restricted to safe same-origin URLs. Production rate limiting requires a trusted ingress header containing one client IP and a separate HMAC secret; missing security configuration fails closed.
- **Search:** `GET /api/organizations/{organizationId}/search` validates a 2–120 character query, optional entity/project filters and bounded pagination; applies per-user/IP rate limits; uses PostgreSQL full-text search with parameterized query terms; and runs under `withOrganizationContext`. Project visibility is enforced by existing RLS on each searched resource. Search covers visible projects, active tasks, comments, active organization members and active file names; member email addresses and file content are not indexed or returned. A project filter limits member results to active project memberships. Migration `0013` adds GIN indexes and `0014` allows the dedicated Search rate-limit scope. PostgreSQL integration cases cover visible and hidden per-entity results, member email nondisclosure, and the unfiltered combined `type=all` result path; these expanded assertions have not run in the current workspace because it has no configured test database.
- **Graph and rate-limit concurrency:** The task and milestone dependency triggers acquire the existing project advisory lock, then update an internal per-project graph-lock row before inspecting graph state. This makes concurrent writes visible under `READ COMMITTED`; a stale `REPEATABLE READ` snapshot fails with PostgreSQL serialization code `40001` rather than permitting a cycle. The row is not directly granted to the runtime role; a fixed-search-path security-definer function checks current project authority before changing it. Rate-limit attempts saturate at the table's 1000-attempt bound while continuing to deny excess requests.

## Request/Data Boundary

1. An API handler authenticates the opaque session and resolves its user on the server.
2. Personal data reads/writes use `withUserContext`.
3. Organization/project data operations use `withOrganizationContext`; callers cannot pass a trusted role, only a minimum role requirement.
4. Membership lookup runs under the request user's RLS context before any tenant business query.
5. RLS policies use `nexora.user_id` and `nexora.organization_id`, set with `set_config(..., true)` inside the same transaction. Project policies additionally require project ownership, a project membership, or organization-manager authority. The user ID must come from the verified session, never the request body/query.
6. Milestone, task, comment, mention, notification, workflow, idempotency, and audit writes share a transaction where required. PostgreSQL remains authoritative; future realtime messages will only signal committed changes.

Mutating API handlers require the exact configured browser origin and reject cross-site Fetch Metadata. JSON is size-bounded and responses are non-cacheable with a stable request ID. The API does not emit `Access-Control-Allow-Origin`; the supported browser/API deployment is same-origin only. Known PostgreSQL serialization failures return a generic `409` conflict without database details. Email endpoints return non-enumerating responses; actual delivery still depends on deployment SMTP configuration.

## Search API

Base path: `/api/organizations/{organizationId}/search`.

- `GET` requires an authenticated session and active organization membership. The route applies a 60-per-user/hour and 120-per-IP/hour rate limit, with the production trusted-ingress IP configuration required.
- Query parameters: `q` (required, trimmed, 2–120 characters), `type` (`all`, `project`, `task`, `comment`, `member`, or `file`), optional UUID `projectId`, `limit` (1–50, default 20), and `offset` (0–10000, default 0).
- Results use `simple` PostgreSQL full-text queries; SQL values are parameterized and the accepted filter set selects only fixed, server-owned SQL fragments. GIN indexes cover project names/descriptions, active task text/labels, comments, and active file names. Member search uses the existing security-definer organization member listing and does not return email addresses.
- Every project-backed source runs inside the caller's organization transaction and remains subject to the table's project-level RLS. A project filter does not grant access to the project. Archived tasks, archived-task comments and deleted files are excluded.
- Response envelope is `{data: {results, pagination}, requestId}` with `no-store`. Each result contains only a display title, short preview/context and an in-app destination; private file bytes and storage keys are never included.
- Search has static schema/migration checks and PostgreSQL integration cases for visible and hidden results across project, task, comment, member, and file types. The project-filtered cases assert that an organization member cannot discover another project's results before membership, and can find them after membership; the unfiltered combined search is also checked before and after membership, and member results are checked for email nondisclosure. The prior PostgreSQL 16 run covered visible/hidden project results only; the expanded cases were skipped in the current workspace because no test database is configured. This is not an exhaustive authorization review.

## Project Analytics API

Base path: `/api/organizations/{organizationId}/projects/{projectId}/analytics`.

- `GET` requires an authenticated active organization member and a project-visible role. It runs under `withOrganizationContext`, checks `can_access_current_project`, uses parameterized organization/project IDs, and reads only existing project-scoped tables subject to their current RLS. Responses use the common `no-store` JSON envelope. No new table, index, migration, background job, or external provider is introduced.
- All task totals include every non-archived task, including subtasks. Completion is based on the project's configured `is_done` workflow status. Project progress is completed tasks divided by all non-archived tasks, rounded to the nearest integer; zero tasks produce `null`/“no data”, not a fabricated 0%.
- An overdue task is non-archived, not in a done status, and has `due_date < CURRENT_DATE` in the database. An overdue milestone is not marked complete and has `end_date < CURRENT_DATE`. Today is not overdue.
- Milestone progress is based on non-archived tasks linked to that milestone and its workflow's `is_done` flag. Milestones with no linked active tasks have no percentage. Counts include all project milestones; the overview displays at most six current milestones.
- Workload shows open, non-archived task counts and explicitly stored effort estimates per project member (including disabled memberships, labeled as disabled), plus unassigned tasks. Tasks without estimates are counted separately. The schema has no member capacity target, so no utilization percentage or capacity claim is produced.
- Recent activity uses matching project/task/milestone/member audit events in the trailing seven days; the count is exact and at most five recent events are displayed. Upcoming deadlines are the next eight dated, incomplete task/milestone deadlines or a non-completed project's target date, on or after the database's current date.
- Health is a rule-based current snapshot, not a prediction: completed/archived status is shown directly; a passed project target or any overdue task/milestone yields “At risk”; otherwise an on-hold status, missing target date, or planned status is labeled explicitly; the remaining active project is “On track”. Each result includes the reason. No trend history or AI-generated insight is included.
- Pure calculation tests cover percentage/health boundaries, and the project-management integration suite asserts metric values and hidden-project denial against PostgreSQL 16. Responsive and accessibility acceptance is still pending.

## Private File API

Base path: `/api/organizations/{organizationId}/projects/{projectId}/tasks/{taskId}/files`.

- `GET` on the collection returns active file metadata to an authenticated project reader. Response metadata contains the file ID, safe filename, MIME type, byte size, uploader display name, version and timestamps; it never returns the storage key or server credentials.
- `POST` on the collection uploads raw file bytes. It requires an authenticated work-authorized project member, same-origin request, canonical `Content-Type`, percent-encoded `X-File-Name`, and an `Idempotency-Key`. Matching retries replay the original metadata result; key reuse for different content returns `409`. The route streams at most 10 MiB, then validates the extension, declared MIME and file signature/content before storing.
- `GET` on `/files/{fileId}` without a token issues a five-minute relative signed URL to an authenticated project reader. Visiting that URL returns the file as a download attachment. The HMAC claim binds organization, project, task, file, version and original user; download rechecks current membership, project access, file version/state, and SHA-256 integrity. Signed downloads are rate-limited.
- `PUT` on `/files/{fileId}` replaces a file's content and metadata. It requires work authorization, same-origin request, and `If-Match` with the current version. A stale version returns `409`; successful replacement increments the version and invalidates older signed links.
- `DELETE` on `/files/{fileId}` requires work authorization and same origin. It immediately hides the file and revokes links; purge logic permanently deletes the file object and metadata after 30 days if the deployment's operator-configured cleanup job runs.

JSON endpoints use the common `{data, requestId}` / `{error, requestId}` envelope with `no-store`; downloaded bytes include `x-request-id`, `no-store`, `nosniff`, and attachment-only content disposition. A task allows at most 20 active files and 100 MiB total. Error responses distinguish authentication, authorization, invalid identifiers/content, size limits, rate limits, stale versions, and unavailable storage without exposing paths or raw content. Upload/replacement cleanup distinguishes known PostgreSQL commit rejections from lost acknowledgements: known SQLSTATE errors roll back and clean staged objects; transport-level uncertainty preserves the object to avoid a committed metadata row pointing to missing bytes. Downloads use the narrowly scoped security-definer function `lock_active_task_file_for_download`, which checks the current project context and locks the active row while the server reads and verifies bytes; viewers do not receive file-table update privileges. Durable encrypted shared storage remains a deployment follow-up.

The `is_current_user_organization_creator` function is narrowly scoped, uses a fixed `search_path`, and exists only to avoid a recursive RLS lookup while bootstrapping a new owner's membership. The application role can execute it but cannot own or alter it. The migration owner must own the function and protected tables.

## Deferred Infrastructure

Redis, queues, a managed object-storage adapter, a dedicated realtime service, and AI-provider adapters are not provisioned in this foundation phase. Private files currently use a local filesystem backend and require a persistent encrypted volume; horizontally scaled app instances must share the same private storage. The cleanup command uses the runtime DB role, purges deleted records after 30 days, and removes unreferenced objects older than 24 hours, but the repository does not configure its schedule. The deployment operator must run and monitor it daily. A shared object-storage adapter is a deployment follow-up. Provider choices remain configuration details; no product requirement depends on a vendor choice.
