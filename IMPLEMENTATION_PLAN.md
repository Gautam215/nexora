# Nexora — Implementation Plan

This plan goes in order, in small steps, and it sticks to what's actually in the project. It doesn't restart anything. It doesn't redo finished work. And it doesn't pull in features or tech that aren't in the PRD and the project documents (`DESIGN.md`, `ARCHITECTURE.md`, `DATABASE.md`, `API.md`, project `AGENTS.md`).

**A note on the PRD source:** there's no `PRD.md` file in the repository. The product source of truth is the Nexora PRD PDF supplied by the user (44 sections, 0–44) and the traceability record in `docs/prd-traceability.md`. If a `PRD.md` is later added to the repository, it must be derived from that PDF and this note must be updated; until then, no document in this plan should claim to quote a `PRD.md` that does not exist.

**Current state, verified in this change:** lint passes (126 files), typecheck passes, the production build passes, and the unit/schema test suite passes with 72 passes and 9 database-integration skips (no disposable database is configured in this environment, so those 9 skip by design; they are not passes). The working tree already contained four local, unpushed changes: the search-test and accessibility fixes, and the PostgreSQL migrator/database guards with automatic runtime grants. Those changes are preserved and are the baseline for this plan, not work to be redone.

**What is already working and preserved:** registration, login/logout, email verification and reset, opaque sessions, rate limits, organization creation and switching, invitations (create, accept, revoke), member role and status management, projects, milestones, tasks and subtasks, dependencies, configurable workflows, Kanban and list views, bulk priority, comments and mentions, project activity, in-app notifications, private task files with signed downloads, permission-aware workspace search, and calculated project analytics. Migrations `0001`–`0022` and runtime grants have passed on a disposable PostgreSQL 16 database in a prior run (85 tests, 0 skips, at that time).

**What is not yet built:** AI (PRD 17–22, 24), realtime WebSockets and presence (PRD 25), logged-in password change, OAuth, active-session management, organization settings and deletion, project and milestone deletion, email notification delivery, durable shared file storage, malware scanning, scheduled file cleanup, health and observability beyond request-failure logs, and production deployment verification. (Health, readiness, and metrics are implemented as of 2026-10-26; cleanup scheduling is defined but blocked on production; storage and scanning still need an external-service decision. Two items from the 2026-10-26 PRD audit were checked 2026-10-26 and are NOT implemented because the PRD gives no implementable policy: see "Open decisions" below: session rotation, and email delivery for notifications, which PRD §13 explicitly defers with "design the architecture so email notifications can be added safely later.")
The Neon migration run authorized in the previous task remains blocked by a runtime permission (direct database connections are denied until the user switches them to "Ask" in Muse settings); it is not part of this plan's phases and must not be retried by working around that block.

## Phase 1 — Fix known errors and close the smallest MVP gaps

- **Goal:** make the existing implementation stable and honest before any new feature is built. No new feature in a later phase starts while a Phase 1 item that it depends on is open.
- **Tasks:**
  1. Fix the email-delivery failure gap: **done in this change (2026-10-25, local, unpushed, verified on a disposable PostgreSQL 16 database, then dropped):** registration, password-reset, and verification-resend no longer swallow SMTP failures. Each route now verifies SMTP delivery before any account or token work, and a delivery failure returns 503 `EMAIL_DELIVERY_UNAVAILABLE` with a generic message, logged server-side as `EmailDeliveryError` with no SMTP detail. Missing configuration still returns 503 `SERVICE_UNAVAILABLE`. During an SMTP outage, eligible and ineligible addresses receive the same 503, because verification runs before any eligibility check, so anti-enumeration is preserved in that state; a transient failure after a successful verify is the only case where a 503 can distinguish an eligible address, and that case is documented here. The invitation route was not changed: it already returns an honest `emailAccepted` flag instead of claiming success, which is the correct pattern for a non-enumerating route that is not required to hide eligibility in the same way.
  2. Verify the four already-local changes (search-test guard, pagination `<nav>`, migrator `-pooler`/`sslmode` guards, automatic runtime grants, Neon timeout, pool error listener) against a disposable PostgreSQL database, and record the result. Do not push them without explicit authorization.
  3. Add the liveness endpoint: GET `/api/health`, unauthenticated, returning process status and database state (`up`, `unavailable`, `unconfigured`) with no secrets or versions. (Implemented in this change; see below.)
  4. Confirm that no test, lint, or typecheck failure remains in the baseline, and that the 9 skipped integration tests are reported as skips, not passes.
- **Files or modules likely affected:** `src/server/email.ts`, `src/app/api/auth/*`, `src/server/db.ts`, `src/app/api/health/route.ts` (new), `tests/health.test.ts` (new).
- **Dependencies:** Phase 0 documents; a disposable database for item 2.
- **Database/API changes:** none for items 1, 3, and 4, except that item 2 verifies migrations `0001`–`0022` and grants on a disposable database. No production migration is authorized by this plan.
- **Tests required:** unit tests for the health endpoint (no database required); integration tests for the email-failure path against a disposable database and a local test SMTP server; the full `npm run check` and `npm run build`.
- **Completion criteria:** `npm run check` and `npm run build` pass; the health endpoint returns 200 with a truthful database field in all three database states; an SMTP failure no longer produces a false success message; the four local changes are either verified on a disposable database or explicitly recorded as unverified.

## Phase 6 — AI (PRD 17–24), only after Phase 5's authorization design

## Open decisions (genuinely need the user; not invented here)

- **Session rotation (PRD §5.1): IMPLEMENTED 2026-10-26 under the user-approved default.** The PRD names "Session rotation" exactly once, in a feature list, with no policy. Approved default: no periodic rotation; rotate/invalidate on privilege change and other security-sensitive events. Organization downgrade/disable and project disable revoke all target sessions in the same transaction (migration 0039, SECURITY DEFINER functions, owner targets refused); project role-only change does not revoke, for the per-request authorization reason documented in ARCHITECTURE.md §7. Password change already revoked all other sessions and keeps the current trusted session; password reset revokes all sessions. Verified by unit tests (`tests/session-rotation.test.ts`) and an integration test (`tests/session-privilege-rotation.integration.test.ts`), plus updated organization/project-management tests that preserve the original 403/404 assertions with fresh sessions after revocation.
- **Email delivery for notifications (PRD §13): IMPLEMENTED 2026-10-26 under the user-approved default.** In-app notifications already existed (recipient-scoped read/unread, preferences, deduplication, mention/assignment/change/membership emitters). Email is now a transactional outbox (migrations 0040–0043) plus a background worker (`scripts/notification-email-worker.mjs`, `npm run notifications:email-worker`): the outbox row is written in the same transaction as the notification, the worker claims (FOR UPDATE SKIP LOCKED), sends, and marks, with backoff and failure after 5 attempts, and fails closed when SMTP is unconfigured. Policy is off by default and opt-in twice over: operator lists event types in `NEXORA_NOTIFICATION_EMAIL_TYPES`, and the recipient enables email for that type (`email_enabled`, default false, in notification preferences). Due-date notifications still need a scheduler (no production environment), which is a separate blocked item, not a gap in the outbox itself. Verified by `tests/notification-email-outbox.integration.test.ts` (default off, opt-in once, policy-off stops email).
- **Alert channel (Phase 4 item 4): IMPLEMENTED 2026-10-27 under the expanded-defaults mandate.** Metrics alerting is in code (`src/server/alerts.ts`, alerts cron job, migration 0049): server-error threshold crossings and database-down (at most once an hour) mail `NEXORA_ALERT_EMAIL` over the existing SMTP path, rate-limited by `alert_state` so there is no spam loop. The recipient value itself is NOT invented: blank means disabled. The documented recommended value is the operator mailbox the user monitors (for this deployment, the Nexora mailbox that already sends mail). Production still needs `NEXORA_ALERT_EMAIL` set and the alerts cron scheduled (Phase A above); until then alerts are disabled by design, not silently active.
- **Shared object storage (Phase 4 item 2) and malware scanning (item 3): ABSTRACTIONS IMPLEMENTED 2026-10-26 under the user-approved defaults, live integrations NOT verified.** Storage: `src/server/storage.ts` (local default; S3-compatible via fetch + SigV4, no SDK; presigned downloads; fail closed on incomplete config; copy-then-verify migration documented in `docs/deployment.md`). Malware: `src/server/malware.ts` (clamd INSTREAM, no SDK; synchronous scan at upload; `clean` / `quarantined` (infected or scanner unavailable) / `pending` (no scanner configured, never clean); downloads blocked with 409 `FILE_QUARANTINED`; rescan script for pending and quarantined files).
